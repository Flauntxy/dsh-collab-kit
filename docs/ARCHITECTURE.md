# 原理与边界

## 为什么用本地 wait，而不是让模型轮询

| 方式 | 空闲时 | 延迟 |
|---|---|---|
| 模型每 30 秒查一次 | 一天几千次回合 | 约半分钟 |
| 模型每 5 分钟查一次 | 一天几百次回合 | 约几分钟 |
| 本工具的 `wait` | 本地进程读几字节 JSON，不调模型 | 通常 1 秒内 |

`wait` 是普通 OS 进程，大约每秒看一次 `flag.json`。空闲时不产生模型调用。

## 数据结构

```
board/messages.jsonl          每行一条：{"ts","from","to","body"}
board/.write.lock             追加时加跨进程锁（Windows msvcrt / POSIX fcntl）
inbox/<身份>/flag.json        {"unread":N,"last_kind","last_ts","seq"}
inbox/<身份>/board_cursor.json  {"offset": 字节偏移}
inbox/<身份>/log_cursor.json    {"pos": {文件: 字节偏移}}
inbox/<身份>/waiter.json      {"pid","started","ts"}  等待任务心跳
inbox/<身份>/daemon.pid       守护进程 pid（可选）
```

游标存在磁盘上，重启后从上次位置继续；断线期间的消息不会丢，恢复后补读。

## 三条唤醒通道

| 通道 | 谁触发 | 典型延迟 |
|---|---|---|
| 新消息 | `post` 写入时 bump flag | 约 0.1 秒 |
| 日志错误 | `daemon` 按 `--interval` 扫一次 | 15~60 秒 |
| 人工 | 人说话 | 即时 |

## 并发

三个地方会并发写，都加了跨进程锁：

| 位置 | 风险 | 处理 |
|---|---|---|
| `messages.jsonl` 追加 | 多进程同时写会丢行 | 文件锁 + flush |
| `flag.json` 自增 | 覆盖丢计数 | 锁内读 → 写（原子替换） |
| 位点文件 | 写一半损坏 | 先写 `.tmp` 再 `replace` |

本机测过：4 进程各写 10 条 → 40/40，无损坏。

## 边界（重要的三条）

### 1. 无法跨机器

只读写本地文件。跨机器请用消息队列 / 共享盘 / HTTP 服务。

### 2. 无法保证投递

这是文件轮询，不是队列：没有 ACK、没有重试、没有顺序保证。
写入成功即视为已投递；对方读没读由 `board_cursor` 判断。

### 3. 等待任务与会话同生共死

这是唯一没法自动化补上的缺口：

- 等待任务是会话的子进程，会话关闭它就没了
- 守护进程能记录事件、能 bump flag，但不能唤醒会话
- 所以重启后要有人在每个对话里说一句，触发一次补挂
  （本机测过：重启后未读与位点还在，补挂后约 1 秒内可再收消息）

建议每个对话在每次回答完自检一次等待任务是否还在，把补挂摊进正常交互。

## 性能（本机大致数字）

| 指标 | 大致范围 |
|---|---|
| 置位延迟 | 约 0.1 秒 |
| 唤醒延迟 | 约 0.3~2 秒 |
| 1000 条消息体积 | 约 200 KB |
| 等待任务 CPU | 可忽略（每秒一次 stat） |
| 守护内存 | 约十几 MB |
