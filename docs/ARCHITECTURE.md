# 原理与边界

## 为什么不用轮询

| 方式 | 空闲成本 | 延迟 |
|---|---|---|
| 每 30 秒检查一次 | 每天 2880 次模型回合 | ≤30 秒 |
| 每 5 分钟 | 每天 288 次 | ≤5 分钟 |
| **等待任务（本工具）** | **0** | **≈2 秒** |

等待任务是一个普通 OS 进程，每秒读一次几字节的 JSON。
它不调用模型，所以空闲时**不产生任何 token**。

## 数据结构

```
board/messages.jsonl          每行一条：{"ts","from","to","body"}
board/.write.lock             追加时加跨进程锁（Windows msvcrt / POSIX fcntl）
inbox/<身份>/flag.json        {"unread":N,"last_kind","last_ts","seq"}
inbox/<身份>/board_cursor.json  {"offset": 字节偏移}
inbox/<身份>/log_cursor.json    {"pos": {文件: 字节偏移}}
inbox/<身份>/waiter.json      {"pid","started","ts"}  等待任务心跳
inbox/<身份>/daemon.pid       守护进程 pid（可选）
```

**位点持久化**：游标存在磁盘上，重启后从上次位置继续，
断线期间的消息不会丢，恢复后补报。

## 三条唤醒通道

| 通道 | 谁触发 | 典型延迟 |
|---|---|---|
| 新消息 | `post` 写入时立刻 bump flag | 0.1 秒 |
| 日志错误 | `daemon` 每 `--interval` 秒扫一次 | 15~60 秒 |
| 人工 | 人说话 | 即时 |

## 并发正确性

三个地方会并发写，都加了跨进程锁：

| 位置 | 风险 | 处理 |
|---|---|---|
| `messages.jsonl` 追加 | 多进程同时写会丢行 | 文件锁 + flush |
| `flag.json` 自增 | 覆盖丢计数 | 锁内读-改-写（原子替换） |
| 位点文件 | 写一半损坏 | 先写 `.tmp` 再 `replace` |

实测：4 进程各写 10 条 → 40/40，无损坏。

## 边界（重要的三条）

### 1. 无法跨机器

只读写本地文件。跨机器请用消息队列 / 共享盘 / HTTP 服务。

### 2. 无法保证投递

这是文件轮询，不是队列：没有 ACK、没有重试、没有顺序保证。
写入成功即视为已投递；对方读没读由 `board_cursor` 判断。

### 3. 等待任务与会话同生共死

**这是唯一无法自动化的缺口。**

- 等待任务是会话的子进程，会话关闭它就没了
- 守护进程能记录事件、能置 flag，但**不能唤醒会话**
- 所以重启后必须有「人」在每个对话里说一句话，触发一次补挂
  （已实测：重启后未读消息与位点**完整保留**，补挂后 1 秒内即可正常收消息）

这也是为什么建议每个对话在**每次回答完**都自检一次等待任务是否还在——
把补挂成本摊到正常交互里，而不是专门去检查。

## 性能

| 指标 | 实测值 |
|---|---|
| 置位延迟 | 0.10 秒（VM 实测 0.02 秒） |
| 唤醒延迟 | 0.3~2 秒（VM 精确实测 0.32 秒） |
| 1000 条消息的体积 | 约 200 KB |
| 等待任务 CPU | 可忽略（每秒一次 stat） |
| 守护内存 | 约 14 MB |
