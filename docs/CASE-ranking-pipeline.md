# 案例：三个对话协作做一条「排行榜视频」流水线

> 真实运行记录（2026-10）。用来说明「多对话分工 + 自动唤醒」在实践中长什么样。
> 内容生产的具体业务已做中性化处理，只看**协作部分**。

## 一、背景

一个人做「排行榜类视频」：选题 → 数据整理 → 内容审核 → 排版成稿 → 渲染出片 → 发布准备。
环节多、单轮耗时长（一期 15 分钟以上），一个对话串行做会不断被上下文打断。

于是拆成三个对话并行：

| 身份 | 分工 |
|---|---|
| **A** | 选题研究、统计口径、风险与配额、文档 |
| **B** | 工具研发：采集与整理脚本、审核工作台、控制台、协作通道本身 |
| **C** | 生产调度：排队跑任务、审核、出片、发布准备 |

## 二、遇到的问题

拆开之后立刻出现协作问题：

1. C 跑完一期，B 不知道
2. A 改了目录结构，B 的脚本路径全断
3. B 修完 bug，C 要等下次对话才知道
4. 最初用「每 30 秒检查一次留言」→ 每天 2880 次模型回合，成本高
5. 重启电脑后，所有「等待」状态全丢

## 三、最终方案

```
A/B/C 各自在自己的会话里挂一个等待任务
        ↓
post 写入 → 置对方 flag → 对方 2 秒内被唤醒
        ↓
poll 读消息 + 归零 → 处理 → 重新挂起
```

配套：

| 组件 | 作用 |
|---|---|
| `post` / `poll` | 消息收发 |
| `wait` | 零成本等待（本地 1 秒轮询） |
| `daemon` | 日志报错也变成唤醒源（每 60 秒扫一次） |
| `status` | 一条命令看所有人是否在线 |
| `selftest` | 通道自检（改代码后回归） |

## 四、实测数据

| 指标 | 结果 |
|---|---|
| 消息写入 → flag 置位 | **0.10 秒** |
| flag → 对话被唤醒 | **2~3 秒** |
| 日志错误 → 唤醒 | 15~60 秒（守护 60 秒一轮） |
| 批量 5 条消息 | 一次 poll 全部读出 |
| 4 进程并发写 | 40/40，无丢行 |
| 空闲 token 消耗 | **0** |
| 重启测试（本机） | 守护自动恢复 ✅ / 数据保留 ✅ / 补挂成功 ✅（共 4 次） |
| 重启测试（另一台机器） | 未读与位点逐字节保留 ✅ / 跨重启消费正常 ✅ / 补挂后 1 秒唤醒 ✅ |

## 五、踩过的坑（都已修）

| 坑 | 现象 | 修法 |
|---|---|---|
| 挂载方式错 | 「说挂了但进程不存在」 | 必须会话内后台任务（`run_in_background`） |
| 重复置位 | 一条消息唤醒两次 | 守护不再对消息置位，只对日志置位 |
| 并发丢行 | 4×10 只成 39 | 写入加跨进程文件锁 |
| 并发丢计数 | 2×10 只记 10 | 锁内读-改-写 + 原子替换 |
| 重启后无唤醒 | 全静默 | 协议：每次回答完自检并重挂 |
| 自测污染 | 测试日志被当成真错误 | 约定 `*.test.log` 与 `_selftest*` 跳过 |

## 六、规则（这个项目的版本）

1. 跨分支的事不经过管理员——直接留言、直接写需求单
2. 每次回答完，自检等待任务在不在，不在就重挂
3. 写消息只用工具，不手改文件
4. 较大的变更主动广播给其余两方
5. 一个身份只挂一个等待任务

## 七、结论

- **省**：从「每天 2880 次轮询」降到「有事才唤醒」
- **快**：2 秒级响应，比人转述快
- **脆**：唯一的弱点是等待任务跟会话同生共死，重启后需要说一句话补挂

如果重做一次，会保留这个设计，但会在第一版就加上：
心跳文件（区分「没挂」和「挂了即死」）、并发锁、以及「每次回答完自检」的协议。
