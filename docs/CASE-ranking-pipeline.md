# 案例：三个对话协作做一条「排行榜视频」流水线

> 真实运行记录（2026-10）。只写协作部分，业务细节已中性化。

## 一、背景

一个人做「排行榜类视频」：选题 → 数据整理 → 内容审核 → 排版成稿 → 渲染出片 → 发布准备。
环节多、单轮耗时长（一期常要 15 分钟以上），一个对话串行做会被上下文打断。

于是拆成三个对话并行：

| 身份 | 分工 |
|---|---|
| **A** | 选题研究、统计口径、风险与配额、文案 |
| **B** | 工具研发：采集与整理脚本、审核工作台、控制台、协作通道本身 |
| **C** | 生产调度：排队跑任务、审核、出片、发布准备 |

## 二、遇到的问题

1. C 跑完一期，B 不知道
2. A 改了目录结构，B 的脚本路径全挂
3. B 修完 bug，C 要等下次对话才知道
4. 最初用「每 30 秒检查一次留言」→ 一天几千次模型回合
5. 重启电脑后，所有「等待」状态全丢

## 三、最终方案

```
A/B/C 各自在自己的会话里挂一个等待任务
        ↓
post 写入 → 置对方 flag → 对方约 2 秒内被唤醒
        ↓
poll 读消息 + 归零 → 处理 → 重新挂起
```

用到的命令：

| 组件 | 作用 |
|---|---|
| `post` / `poll` | 消息收发 |
| `wait` | 本地等 flag（约 1 秒轮询一次） |
| `daemon` | 可选：日志报错也 bump flag |
| `status` | 看各身份是否在线 |
| `selftest` | 改代码后自检 |

## 四、本机测到的数字

| 指标 | 结果 |
|---|---|
| 消息写入 → flag 置位 | 约 0.10 秒 |
| flag → 对话被唤醒 | 约 2~3 秒 |
| 日志错误 → 唤醒 | 15~60 秒（守护 60 秒一轮） |
| 批量 5 条消息 | 一次 poll 全部读出 |
| 4 进程并发写 | 40/40，无丢行 |
| 空闲时模型调用 | 0（`wait` 不碰模型） |
| 重启后 | 未读与位点保留；补挂后约 1 秒可再收 |

## 五、踩过的坑（都已修）

| 坑 | 现象 | 修法 |
|---|---|---|
| 挂载方式错 | 「说挂了但进程不存在」 | 必须会话内后台任务 |
| 重复置位 | 一条消息唤醒两次 | 守护只对日志置位 |
| 并发丢行 | 4×10 只成 39 | 写入加跨进程文件锁 |
| 并发丢计数 | 2×10 只记 10 | 锁内读 → 写 + 原子替换 |
| 重启后无唤醒 | 全静音 | 约定：每次回答完自检并重挂 |
| 自测污染 | 测试日志被当成真错误 | 约定 `*.test.log` / `_selftest*` 跳过 |

## 六、这个项目用的规则

1. 跨分支的事不经过管理员——直接留言
2. 每次回答完，自检等待任务在不在，不在就重挂
3. 写消息只用工具，不手改文件
4. 较大的变更主动广播给其余两方
5. 一个身份只挂一个等待任务

## 七、小结

轮询模型改成有事才醒，响应大概在秒级。唯一弱点还是：`wait` 跟会话同生共死，重启后要说一句话补挂。

如果重做，会在第一版就加上心跳文件（区分「没挂」和「挂了即死」）、并发锁，以及「每次回答完自检」的约定。
