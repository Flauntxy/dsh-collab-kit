# 协作规则 · 建议（不是强制）

> 这些是本项目实践后总结的「建议」，按你的团队情况改。
> 规则的目的是**减少一次中转**，不是为了管控。

---

## 一、跨对话的事不经过管理员（建议）

如果每个人都在等管理员转达，消息就要走两跳、延迟一次。

**建议约定**：

| 情况 | 直接做 |
|---|---|
| 想确认某件事 | 直接给对方留言问 |
| 认为某件事该别人做 | 直接写需求单留言给对方 |
| 发现别人范围内有问题 | 直接留言指出 |
| 做完一件事 | 在对话里说一句「做了什么」即可 |

**唯一例外**：自己无法决策的（需要预算、需要改变目标、涉及外部合规），
整理成一页发给「协调者」角色。

> 这一条可以减少大量「管理员转述」的往返，但不是必须——
> 小团队或边界清晰时，直接沟通往往更高效。

---

## 二、每个人每次回答完，自检一次等待任务

**建议**：把「自检 + 重挂」写进每个人的行为准则。

```bash
python collab.py status          # 看自己在不在
# 或
python collab.py wait --as X --timeout 14400   # 不在就重挂
```

原因：等待任务会因超时、重启、会话重建而消失，
它消失后你**不会知道有人给你发过消息**。

这是本方案里唯一需要人（或 agent）主动维持的东西。

---

## 三、写消息只用工具，不手改文件

手工往 `messages.jsonl` 追加**不会置 flag**，对方可能永远不知道。

```bash
python collab.py post B "内容" --from A
```

---

## 四、区分「同步信息」和「需要对方行动」

| 类型 | 写法建议 |
|---|---|
| 通知 | 一句话说清「发生了什么、影响谁、要不要动」 |
| 需求 | 标题带编号（REQ-001），写清：现象 / 期望 / 验收 / 优先级 |
| 阻塞 | 开头标 **P0**，并说明「不做会怎样」 |

对端读到的第一行就能判断要不要立刻处理。

---

## 五、一个身份只挂一个等待任务

同一身份开两个等待任务，会在同一个 inbox 目录里抢写游标，
表现为「有时能收到、有时漏」。

不同身份互不干扰，可以同时挂。

---

## 六、变更要广播（可选）

如果改动会影响别人的工作（改目录结构、改接口、改约定），
**主动给相关方各发一条**，而不是等对方发现。

格式建议：

```
【变更通知 · 做了什么】
① 改了什么
② 影响谁 / 何时生效
③ 对方需要做什么（没有就写「无需操作」）
```

---

## 七、小团队可以精简

2 个人、边界清晰时，上面六条可以只保留：

1. 写消息用工具
2. 每次回答完自检一次
3. 一个身份一个等待任务

其余按需加。

---

## 开工第一步（建议做成硬性）

每次开始干活前，先检查等待任务在不在：

`ash
python collab.py status
`

看到自己的「等待任务」是 未挂，就立刻重挂：

`ash
python collab.py wait --as <身份> --timeout 28800
`

**为什么定为第一步**：等待任务被唤醒后会退出（这是它能唤醒会话的原因）。
消费完忘了重挂，就会静默失联——对方发了消息你完全不知道。

真实案例：某次醒来后未重挂，漏了 4 条留言，其中一条是会导致成品出错的 bug 报告。

### 配套三条

1. 开工先查状态
2. poll 完**立刻**重挂，不要攒到下一轮
3. 收工前确认 waiter.json 里的 pid 还活着
